# Profile below kernel level: hydro, mesh, precision presets, 2026-11-06

Sedov 3D jittered, HLLC, double unless named, 40 steps, one A100. luna-cpp main 1052464, voronoi-cpp ffb6060, built Release with `-g -lineinfo` (device code optimised as before; 15.34 against 15.37 ms per
static step). Clock by job: 1095 or 1305 MHz, stated. Rates in G cell updates/s (1 cell update = 7.95 face updates). Scripts: `scripts/profile_a100.sh`, `profile_table.py`, `profile_source.py`, `profile_arrays.py`,
`profile_exp_table.py`, `profile_nsys.py`, `preset_figures.py`. Scratch switches: branch `profile-exp`, never for main. Data: voronoi-cpp/build-roofline/prof, logs/prof-*.out. TLB misses: no counter exists on A100 in ncu 2026.2;
indirect evidence only (pointer chase flat at 334 ns from 128 MiB to 8 GiB, research_notes/roofline_2026-11-05.md).

## Hydro: what would give the most (estimates labelled)

1. `grad32` as default for moving and static: measured +14 % static, +10 % whole step, no code to write. Cost: not main's bits; accuracy per the precision study; memory 64 B/cell less.
2. An owner bit in the list entry: no scattered owner loads in `update` or `other(f, i)` of the sweep, 27 % of update's samples, 16 % of the sweep's. Storing the other cell in the list saved the sweep 6 % in hydro_speed (g2), where a hydro pass rebuilt it; written by the mesh it costs no pass. Estimate: update +25 %, sweep +8 %; hydro static +8 %, whole step +5 %. Open since hydro_speed, now with numbers.
3. Faces numbered in owner order by the mesh (voronoi-cpp): measured +8 % hydro; +5 % whole step (estimate), no copy pass. Items 2 and 3 overlap in update.
4. Fewer registers in the sweep without splitting its loads (refuted splits doubled DRAM): reloads are the compiler's answer to 148 registers. Halving them (warps 17 -> 34 %) has the fluxes as a precedent, 80 registers at 0.57 G/s. Estimate: sweep +30 to +50 % if it comes with the same memory traffic, hydro +10 to +17 %; no proven route, m2 of hydro_speed failed by stacking.
5. Not worth doing: reuse between passes, sorting cells, a sort by list length.

### voronoi-cpp: what would give the most (estimates labelled)

1. A re-sort when the order has decayed (cells by Morton, tetrahedra and faces after them): the smooth flow runs at half speed by step 500 (measured), and that is what a long moving run sees. Estimate: back to the early rate, every few hundred steps; the sort's cost not measured. Sedov does not show it.
2. Number the faces by owner, or sort them when the update has touched many: +8 % hydro measured with the hydro's own copy; in the mesh `faces`, `cell sums` and `sort` gain too (they read `owner`, `neighbour`, rings by face): estimate +5 % whole step.
3. `cells_incremental` and face numbers run over all cells and all tetrahedra: 0.21 + 0.54 ms at 128^3, 66-96 % waiting on `marked`, `edges(t)` for items mostly unchanged. A list of touched cells, as the repair has: estimate -0.5 ms at 128^3, +1.5 % step; bench more.
4. `renumber(old_face)` in cell sums holds 41 %: on Sedov nearly all faces keep their number; if numbers were stable, the kernel reads no renumber table: estimate cell sums +30 %, step +1.5 %.
5. Launches: 66 per step, 30 from repair rounds with almost nothing to do. Stop launching `unlist` and `release` when empty, and merge repair rounds under a threshold into one launch: estimate -0.3 ms of 2 ms; matters below 64^3, not at 128^3 and above (6 %, under 1 % at 256^3).
6. Ring walks (bench): rings as arrays of the face rather than edge walks through `vertex`: 3.5 ms each at 128^3 on the smooth flow; memory is the known cost of that choice (`face_rings_pool`). Not estimated.
