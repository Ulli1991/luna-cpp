# Derivatives of the hydro, step L1: hand-written tangent and adjoint (2026-11-19)

Branch `autodiff-l1` from main 5b3f706, worktree /raven/u/uli/luna-cpp-ad. [M] measured, [I] inference or design.
Issue #12, docs/ideas.md rows L1, L2, L7, L5/L9/T8, O2/J4.

**Route.** On 2026-11-06 the owner decided to keep autodiff in C++ through Enzyme. On 2026-11-19 he changed that to hand-written
derivatives, so the Enzyme route of #12 is superseded. No Enzyme or LLVM was built: no job was submitted for it, so nothing had to be
cancelled or deleted.

The derivatives are hand-written in both modes, and each mode is a product of its own:
- **tangent-linear (forward):** J v;
- **adjoint (reverse):** Jᵀ w.

Each derivative sits beside the forward function it differentiates, in the same file and under the same name with a suffix. Both run
in the solver's own kernels, so the same code runs on the host and on the A100.

## What is in the branch

| Forward | Tangent | Adjoint | File |
|---|---|---|---|
| `primitive` (U → W, RAMSES floors) | `primitive_tangent` | `primitive_adjoint` | euler.hpp |
| `half_step` (MUSCL-Hancock predictor) | `half_step_tangent` | `half_step_adjoint` | euler.hpp |
| `detail::side`, `side_with`, `to_lab` | `side_tangent`, `side_with_tangent`, `to_lab` (it is linear) | `side_adjoint`, `side_with_adjoint`, `to_lab_adjoint` | euler.hpp |
| `HLL::flux` | `HLL::flux_tangent` | `HLL::flux_adjoint` | euler.hpp |
| `HLLC::flux` | `HLLC::flux_tangent` | `HLLC::flux_adjoint` | euler.hpp |
| `Sweep` (least-squares fit and face-centroid limiter, one cell) | `limited_gradient_tangent` | `limited_gradient_adjoint`, `neighbour_bar` | finite_volume.hpp |
| `FaceFlux::side` (half step plus g·r, positivity fallback) | `FaceFlux::side_tangent` | `FaceFlux::side_adjoint` | finite_volume.hpp |
| `step` (static, order 1) | `FiniteVolume::step_tangent(dt, dq)` | `FiniteVolume::step_adjoint(dt, qbar)` | finite_volume.hpp |

Helpers:
- `primitive_branches`, `HLL::branches` and `HLLC::branches` (with `HLLC::waves`) return the forward's branch pattern;
- `FiniteVolume::limited_gradient` is Sweep's double path written as a function of the stencil, with the clip pattern;
- `FaceFlux::side_value` is `side()` as a function.

**Scope.**
- Static mesh, order 1, the per-face loop.
- Double throughout (`Precision<>`); a static_assert enforces it.
- dt fixed: its dependence on Q (the CFL rule) is not differentiated, as in LUNA's default (see row 6 of the LUNA table below).
- `require_derivatives()` throws on anything else.
- The code is written for any D, but only D = 3 is instantiated and tested; 2D is a next step.

**`step_tangent(dt, dq)`** is `step()` with the tangent carried in the same four passes:
1. primitives → dW;
2. sweep → g and dg, with the fit and the limiter recomputed together;
3. fluxes → F and dF per face;
4. update → Q and dq.

Q comes out bit for bit equal to `step()`'s on the host [M]. On the A100 it differs at the rounding level, 1e-14 to 5e-13 over 3
steps (see "A100").

**`step_adjoint(dt, qbar)`** takes Q̄ⁿ⁺¹ in `qbar` and leaves Q̄ⁿ there. Q stays Qⁿ, which the caller restores from a checkpoint. It
recomputes the forward primitives and gradients, then runs three passes, all per cell and without atomics, so the bits are the same
every run:
1. **fluxes:** each face's flux adjoint, taken from both of its cells → the cell's W̄ and ḡ;
2. **sweep:** the gradient's adjoint → the fit's b̄ (V·(D+1) per cell), each variable's bound bar and the face it came through, and the
   cell's own W̄;
3. **gather:** each cell collects its neighbours' b̄ and bound bars, then applies the primitive adjoint into Q̄.

**Shared code with the forward.** No forward function was changed. Each `*_tangent` and `*_adjoint` recomputes the forward
intermediates it needs, with the same expressions, and calls the forward where it can:
- `flux()`, `half_step()` and `primitive()` give the values;
- `HLLC::waves()` repeats `flux()`'s wave speeds, so its branch pattern is the forward's.

Templating the per-face math on a dual type, so that forward and tangent share one source, would change the forward's code and so
possibly its bits. The same holds for Sweep calling `limited_gradient()`, which would make the tangent step's Q bit-equal on the A100
too. Both are next steps, each with a bits and speed check against main.

**Tests.** `hydro_derivatives_test` (src/test) is opt-in: CMake `-DLUNA_DERIVATIVE_TESTS=ON`, off by default, so CI and the default
build are as before. It runs on the default execution space (host or A100).

**Per piece:** 20000 random samples per piece, in a kernel.
- The tangent is compared with central differences at h = 1e-6 relative.
- A sample is kept only if the branch pattern at x + h dx and x − h dx equals the pattern at x.
- The adjoint is compared with the tangent by the dot test, ⟨w, J v⟩ = ⟨Jᵀ w, v⟩, relative to Σ|terms|.

**Over whole steps:** a jittered mesh of 1000 cells, with HLLC and HLL, 1 and 3 steps, a smooth state and a rough one (30 % noise).
- The forward bits are checked against `step()`.
- J dq is compared with central differences.
- The dot test runs over 1 and 3 steps, the adjoint going backwards from checkpoints of Q.
- `step_adjoint` must leave Q unchanged.

## Branches: the derivative at each switch

Every forward function here is piecewise smooth. The hand-written derivatives take, at every switch, **the derivative of the branch the
forward took** (a one-sided derivative). Only the selected branch is ever differentiated, so an unselected branch cannot put a NaN into a
tangent or a bar. This is LUNA's "poisoned VJP" problem, which hand-written code does not have. The tests keep only samples with an
unchanged branch pattern within ±h, and count the ones they skip.

| Switch | Forward | Derivative used | Measured |
|---|---|---|---|
| density floor | ρ = max(U₀, smallr) | 0 in U₀ when floored, else 1 | not sampled: floors need ρ < 1e-10 |
| energy floor | e = max(E − ½ρv², smalle ρ) | smalle dρ when floored | not sampled |
| face side fallback | Wf = W when ρ_f ≤ 0 or P_f ≤ 0 | dW: the side is the cell state | 285 fallback samples, FD 2.8e-9 |
| HLL/HLLC S_L = min(·,·), S_R = max(·,·) | min/max of the two sides' wave speeds | the derivative of the side picked | all samples |
| HLL cases | F_L if S_L ≥ 0, F_R if S_R ≤ 0, else the HLL star | per case | three cases |
| HLLC cases | F_L, F*_L, F*_R, F_R (LUNA's order) | per case; at S_M = 0 the left star case is used, as the forward does | four cases |
| HLLC c² guard | c² < 0 on either side → F_R; c = 0 when c² ≤ 0 | F_R's derivative; dc = 0 where c² ≤ 0 (no division by c) | needs P < 0: not sampled |
| HLLC 1e-20 guard (`nonzero`) | divisor replaced by ±1e-20 when below it | 0 for the replaced divisor (it is a constant) | not sampled (needs a divisor below 1e-20) |
| limiter clip | each face can scale g_v by (bound − W_i)/(g_v·o_f), in face order | at a fixed clip pattern the result is g0_v (bound − W_i)/(g0_v·o_last): only the last clip and its bound matter, so the derivative needs (last face, bound neighbour) per variable and no per-face tape | 651 + 131 clipped samples, FD 9.1e-9 |
| clip to zero | bound on the wrong side of W_i → g_v = 0 | 0 | 131 samples |
| bound neighbour (max/min over neighbours) | the neighbour that holds hi or lo | its dW (first one on a tie) | in the clipped samples |
| tiny-face rule | faces below 1e-6 of the surface do not count for the range or the clip | geometry, fixed on a static mesh | n/a (static) |

**Why one clip.** On a fixed clip pattern, the limiter reduces to a single scaling, which keeps the derivative small. The clips multiply
the gradient by positive factors. The last clip k sets g_v·o_k = bound − W_i, and that result does not depend on the earlier factors. So
the limited gradient is g0_v (bound − W_i)/(g0_v·o_k), with g0 the unlimited fit, unless some clip set it to zero.
- The tangent and the adjoint need only (k, bound neighbour, upper or lower, zero) per variable, which is 5 small integers.
- The fit is linear in W, with M fixed by the geometry. Its adjoint is one more solve with the same Cholesky factor (M is symmetric).
- `step_adjoint` stores b̄ (20 doubles a cell in 3D) and lets each cell gather from its neighbours. This avoids atomics and storing
  anything per face.

**Across a switch.** What a derivative means across a switch:
- **Continuous switches** have one-sided derivatives that differ (a kink). They are:
  - the min/max of the wave speeds;
  - the HLLC and HLL cases (the fluxes meet at the switches);
  - the clip (the factor goes to 1 as W_i + g·o reaches the bound, and to 0 as the bound reaches W_i);
  - the bound neighbour (a max/min);
  - the floors (a max).

  The derivative used is a valid element of the generalised (Clarke) gradient. Gradients summed over many steps are well defined
  almost everywhere, and an optimiser sees kinks.
- **Discontinuous switches** are three:
  - the positivity fallback, which jumps from the extrapolated state to W;
  - the 1e-20 guard, at a divisor of exactly 0 (the sign of ±1e-20 flips);
  - the tiny-face rule (moving mesh only).

  There the forward value jumps. The derivative is that of the branch taken, so it misses the jump. Finite differences across such a
  switch are meaningless; the tests skip those samples, or compare one-sided differences.

### Against LUNA's smooth-tangent minmod, and a proposal

LUNA's `limiter_tangent_eps` (src/luna/hydro/slopes.py:72-101) keeps the forward bit for bit exact minmod. It replaces only the tangent
with the JVP of a smoothed minmod:
- A = sqrt(a² + e²), B = sqrt(b² + e²);
- soft_min = ½(A + B − sqrt((A − B)² + e²) + e);
- result = ½(a/A + b/B)·soft_min;
- e = eps × the cell's (ρ, sqrt(P/ρ) per velocity, P), under stop_gradient.

Why LUNA has it. At a flat state, minmod's exact derivative is 0, so the tangent of the step is first order. On Kelvin-Helmholtz this put
the tangent's growth rate −54 % to −7 % below theory; eps = 1e-4 brings it to +0.011 % (LUNA docs/AUTODIFF.md:467-566). It exists only for
minmod (LIMITER=0), and it is off by default.

luna-cpp's face-centroid limiter behaves differently at the two kinds of crease [I, from the code]:
- **At an exactly flat state** (all neighbours equal, LUNA's case), g0 = 0, so no clip fires and the tangent is the *unlimited*
  least-squares fit of dW. The tangent is second order, not first: luna-cpp does not have LUNA's flat-state problem. It errs the
  other way. The true directional derivative there is the limited gradient of the perturbation itself, which is positively
  homogeneous but not linear, and the tangent ignores the clips the perturbation would trigger.
- **At a local extremum with a nonzero slope,** the bound sits on the wrong side of W_i, the clip goes to zero, and the derivative of
  that variable's gradient is zero. The tangent is first order there: at the top of a wave, and wherever noise makes extrema. The
  forward does the right thing for stability. The derivative is correct for the forward, but it tells an optimiser nothing about how
  the slope there would respond.

Which of these matters for luna-cpp's uses (KH growth rates, sound waves, inversions) is to be measured, as LUNA did.

**Proposal** (not implemented; the scheme stays unchanged):
1. **Default derivative:** the exact one-sided derivative, as now. It is what the tests verify, and what an adjoint for verification
   and FD agreement needs.
2. **Option `tangent_smoothing = eps` (off by default),** following LUNA's design. It changes only the derivative functions, never the
   forward:
   - in `limited_gradient_tangent` and `_adjoint`, replace the clip factor s = (bound − W_i)/(g0·o) by a smooth surrogate
     s_ε = soft_min(1, (bound − W_i)/(g0·o)) for the purpose of its derivative;
   - replace the zero clip (bound on the wrong side) by a factor with derivative ε-scaled. It can use LUNA's soft_min with the same
     per-variable scale (ρ, sqrt(P/ρ), P);
   - apply the same to the bound neighbour: replace the hard max/min by a softmax derivative over the neighbours within ε of the
     bound.
3. **Smooth tangents for the Riemann switches** are not proposed now. LUNA measured that the S_M = 0 kink is not the dominant error
   (AUTODIFF.md:512-518). HLLC is continuous across its cases.
4. **Measure before keeping**, as LUNA did: the tangent's growth rate on KH (2D) and the sound wave against theory, with and without
   ε. Add a row to docs/tried.md.

Unlike LUNA's, the smoothing would cover luna-cpp's actual limiter, the face-centroid one in 2D and 3D. LUNA's covers only minmod; it
has none for MC or van Leer, and its own AUTODIFF.md:471 notes the same crease there. For the 1D limiters (minmod, van Leer), the same
option would apply to finite_volume_1d.hpp once 1D has derivatives.

**Reading** [I]:
- Forward mode costs 2.3× a double step and reverse mode 4.1×. Both include the forward and are computed with no tape.
- LUNA's JAX derivatives cost JVP 2.7-3.5× and VJP 4.8-5.6× of an XLA forward step, which is itself slower than its Pallas kernel.

**Levers** (not tried; each gets a docs/tried.md row when measured):
1. The tangent sweep walks a cell's list four times: fit, range, clip, tangent right-hand side. Each entry's face, neighbour and |area|
   are recomputed per access. Two walks, as Sweep does, should bring it near 1.5×.
2. The flux adjoint evaluates every face twice. Alternatives:
   - one per-face pass storing L̄ and R̄ (80 B a face, about 640 B a cell), then per-cell side adjoints;
   - colours or atomics, as in docs/ideas.md.
3. HLLC's adjoint takes its upwind state by reference to one of two arrays. The forward found that this puts both in local memory on
   the A100 (README, Limitations). Copy it entry by entry as `flux()` does.
4. The tangent's update reads F and dF and writes Q and dq: twice the bytes, so 2× is its floor.

## LUNA's autodiff: lessons and weaknesses

Read-only study of /raven/u/uli/LUNA (code, docs/AUTODIFF.md, CHANGELOG, CODE_NOTES, tests). The references are LUNA's files; Python paths are under its src/luna/.

**What it differentiates and how.**
- **Plain JAX AD through the XLA MUSCL-Hancock step.** `build_simulate` scans `evolve.step` in `lax.scan` with `@jax.checkpoint` on
  the body (luna/autodiff/rollout.py:20, 104-109).
  - That stores one carry per step and recomputes the step's internals backwards.
  - Gradients are with respect to source parameters θ and U0, in forward or reverse mode (`autodiff_grad_mode`).
  - `autodiff_checkpoint="revolve"` is Griewank's binomial checkpointing as a custom_vjp over `fori_loop`, in reverse mode only
    (time_integration/revolve.py:165-200). It is bitwise identical to per-step checkpointing.
- **`autodiff_mode` changes the run:**
  - it forces the XLA hydro (Pallas refuses: "the kernels have no VJP; autodiff differentiates XLA", muscl_hancock_pallas.py:139-140);
  - it gives gravity an implicit adjoint (a custom_vjp FMG);
  - it runs OU forcing in the state's precision;
  - it refuses AMR, particles, cosmology and `allow_first_order_faces`, so an unphysical face state is a NaN loss.
- **The only hand-written rules** are the smooth minmod tangent (custom_jvp), the Poisson adjoint, the cooling and Rodas3 VJPs, and
  revolve. There is no hand-written hydro derivative.
- **NaN-safe guards** in `_hllc_core` (fluxes.py:51-106) exist because `jnp.where` evaluates both branches, and 0 × NaN poisons the
  cotangent:
  - the safe sqrt, `c = where(c2 > 0, sqrt(where(c2 > 0, c2, 1)), 0)`;
  - the `ok` gate;
  - `_nz` (±1e-20).

  The `_nz` guard was added after "the NaN sqrt partial poisoned the VJP". HLL has the safe sqrt only.
- **dt:** `autodiff_dt_mode="stopgrad"` by default (stop_gradient before `compute_dt`). Every test and benchmark uses a fixed dt.
- **Precision:** FP64 is assumed (x64 off by default, but the tests and docs assume it).
- **Multi-device:** reverse mode works through shard_map halos. Forward mode is refused where a collective has no JVP rule.

**Weaknesses, with evidence.**
1. **No gradient on the fast path.** Pallas has no VJP, so gradients run on XLA. FP64 Pallas is about 2× XLA on MI300A, and at 512³ only
   Pallas fits (CODE_NOTES.md:86-93).
2. **Memory.**
   - Gradient/forward memory is 5.3-5.6 at 128-256³ (AUTODIFF.md:107-114).
   - Per-step checkpointing dies at 128³ after about 255 steps (SIGSEGV), and at 256³ after 120 steps out of memory at 88 GiB.
   - "The limit is the step, not the tape": the forward step carries about 25 N³ temporaries.
   - A 1-step JVP at 448³ peaks at 15.7 states.
3. **Flat-state tangent is first order** at limiter creases (the KH numbers above). It is smoothed for minmod only.
4. **Piecewise differentiability.** The Taylor remainder is first order, with and without the limiter, because HLLC's wave cases also
   kink (test_autodiff_identities.py:300-317). A central FD across a shock is invalid. Its FD test does not know where the switches
   are, so its agreement floors at the kinks. The best over h = 1e-3 to 1e-5 is 1.0e-7 for the global ½⟨U, U⟩ and 3.9e-5 for one
   cell (test_autodiff_validation.py:67-95). luna-cpp's step test reaches 5e-10 in every cell of a smooth state. At a switch it
   checks the one-sided difference instead.
5. **NaN holes left.**
   - HLL's 1/(S_R − S_L) and 1/ρ in both cores are unguarded.
   - An unphysical face state is a NaN loss by design in `autodiff_mode`.
6. **dt derivatives.** `dt_mode="diff"` is untested (no test in tests/), and the default drops dU/d(dt).
7. **FP32 gradients are never computed.** The only check rounds the input to FP32 and differentiates in FP64: rel 1.2e-4, conditioning
   amplifying the rounding about 2000× over 4 steps.
8. **No forward mode through gravity or cooling** (custom_vjp only), so the transpose identity is checked for hydro only.
9. **ROCm workarounds and crashes:** HIP_LAUNCH_BLOCKING (gravity 3.1× slower), AMD_SERIALIZE_COPY, gradients only under jit, and a
   1024³ miscompile that gave silently wrong gradients until an `optimization_barrier`.
10. **Untested:**
    - HLL and van Leer under AD;
    - 1D and 2D AD;
    - adaptive dt;
    - FP32-computed gradients;
    - the NaN guards beyond one negative-pressure face.

**What LUNA does well, and luna-cpp copies:**
- the dot test at 1e-11, with "teeth" (a 1.01× corrupted adjoint must fail);
- conservation identities (d total mass / dU = (1, 0, 0, 0, 0));
- a degeneracy guard (a nonzero gradient in at least half the cells);
- central FD at smooth states and one-sided FD at shocks;
- sharded against single-device gradients;
- revolve.

**How luna-cpp's design closes each weakness:**

| LUNA weakness | luna-cpp |
|---|---|
| 1. no derivative in the fast kernels | the tangent runs in the same passes as `step()` (the forward bits are unchanged); the adjoint is a FiniteVolume method using the same mesh data and loops; both are Kokkos code on the A100 from the start [M: host; A100 below] |
| 2. memory from AD temporaries | no tape: the adjoint stores one Q per checkpoint (40 B a cell static) and recomputes the step. Derivative rows: forward mode about 200 B a cell plus 40 B a face per tangent; reverse 380 B a cell, freed between steps (see "Memory and checkpointing") |
| 3. flat-state tangent | at an exactly flat state the face-centroid limiter does not clip, so the tangent is the unlimited fit, second order. The crease is at extrema with a nonzero slope (the zero clip); proposed: an optional smooth tangent there, as LUNA's minmod but for the limiter luna-cpp runs (above) |
| 4. kinks | the same in principle (the scheme is piecewise smooth). The tests state the branch pattern and skip samples that cross it, and count them |
| 5. NaN in unselected branches | none by construction: only the taken branch is differentiated; no division by c where c² ≤ 0; guarded divisors have derivative 0 |
| 6. dt | dt fixed now. A dt derivative is a scalar: dQ/d(dt) is one more tangent direction (∂step/∂dt), and the CFL rule's derivative is a min over cells, so the derivative of its arg-min cell. Test it, unlike LUNA |
| 7. FP32 | stated: the derivatives are double. A reduced-precision forward (grad16, the 3D default) is linearised at its stored state; next, measure the gradient error of a grad16 forward against double, as LUNA did by input rounding but on the real policy |
| 10. untested | HLL and HLLC, every case counted; the step on both solvers; next: 2D, 1D, the moving step |
| teeth | to add: a corrupted adjoint (1.01×) and a tangent with the clip's bound term dropped must fail the tests |

**What could go back to LUNA** (proposals only; LUNA is not edited):
1. **A custom VJP for the Pallas kernel,** written as luna-cpp's adjoint is:
   - per-face flux adjoints recomputed from both sides, no per-face tape;
   - the gradient's adjoint as one more solve, or for 1D minmod the single-clip rule.

   That would give gradients on the fast path and remove the "25 N³ temporaries" limit.
2. **The single-clip rule for slope limiters:** on a fixed pattern only the last active clip matters, so a VJP needs a few integers per
   cell, not the whole where-tree.
3. **Guard HLL's 1/(S_R − S_L) and 1/ρ** as `_hllc_core` is guarded, or compute only the taken branch in a custom rule.
4. **A smooth tangent for MC and van Leer** (the crease AUTODIFF.md:471 names), with the same e scale.
5. **A test of `autodiff_dt_mode="diff"`,** and FD tests for HLL and van Leer.
6. **Branch-pattern-aware FD tests** (keep a sample only if x ± h has the same pattern; count skips). They give 1e-8 agreement instead
   of a floor at kinks.

**External check against LUNA's gradients** (not done today). It needs a step derivative in luna-cpp's 1D solver (finite_volume_1d.hpp,
fused kernel). Plan:
- the 1D Sod tube or the sound wave at N = 64;
- minmod, HLLC, fixed dt, 10 steps. LUNA's own gradient tests use 3D grids (16³, `_sod_state` in
  tests/test_autodiff_validation.py:102), so LUNA runs in 1D through the same driver as the 1D comparisons in hydro1d_test;
- a loss ½⟨U, U⟩;

The two codes agree in their forward 1D states to 1e-12 already (hydro1d_test), so their gradients should agree to about the same,
away from switches.

## Step-level design

### Forward mode (tangent-linear): sensitivities to a few parameters

**Done for the static step: `step_tangent(dt, dq)`.** For k parameters p, the caller seeds dq = ∂Q⁰/∂p_i, one per tangent. Source terms
or an EOS parameter enter as one more term in the tangent of the pass that uses them. Each step then propagates J dq alongside Q, with
no storage beyond the tangent rows.

**Memory per tangent (3D, double)** [I, from the row sizes]:
- persistent dq: 40 B/cell;
- transient: dW 40, dg 120, and dF 40 B a face, which is 7.95 faces a cell for jittered points (measured at 128³), so about 300 B/cell;
- in all, about 500 B/cell per tangent.

With k tangents the per-face and per-cell work can be batched: the forward intermediates (W, g, the Riemann waves) are shared, and only
the tangent arithmetic multiplies. A `Cells` of V·k columns and loops over k inside the kernels is the next step for k > 1.

**Cost per tangent:** the forward and one tangent take 2.0-2.3× a double forward step (see "Cost"), so one tangent adds 1.0-1.3 steps.

**Use cases:**
- sensitivity of a run to a few parameters: γ, an initial amplitude, a source strength;
- the tangent growth rate of instabilities (KH, as in LUNA's stability study);
- error propagation;
- Newton-Krylov for implicit steps (J v products).

### Reverse mode (adjoint): gradients with respect to whole fields

**Done for one static step: `step_adjoint(dt, qbar)`.** It needs Qⁿ (the checkpoint), dt, and the mesh. It recomputes primitives and
gradients (one forward sweep). What each pass needs:

| pass | reads | writes |
|---|---|---|
| forward recompute | Qⁿ, geometry | prims, g (scratch the forward uses anyway) |
| fluxes adjoint | prims, g, Q̄ⁿ⁺¹ of both cells of each face, face geometry | W̄, ḡ per cell (40 + 120 B) |
| sweep adjoint | prims, ḡ, the cell's list and geometry | b̄ (160 B), bound bars and faces (60 B), W̄ += own term |
| gather | b̄ and bound bars of the neighbours, prims (Q) | Q̄ⁿ (in place) |

**Recompute against store.** Everything is recomputed from Qⁿ. Each face's flux and its adjoint are computed twice, once from each
cell, so the adjoint needs no per-face rows and no atomics. The alternatives are:
- (a) store the face states and Riemann waves in the forward: about 30 doubles a face, 1.8 kB/cell, too much at 2252 B/cell;
- (b) atomics: half the flux adjoint work, but the bits vary run to run;
- (c) faces in colours (docs/ideas.md has the forward version).

Measure (c) and (b) against the current recompute if the fluxes adjoint dominates. Measured: the flux adjoint pass is the largest part of the reverse step, 23 of 53 ms at 128³ (see "Cost").

**Memory of the reverse step** (3D, double) [I]:
- the rows W̄, ḡ, b̄, bound: 380 B/cell. ḡ (120 B) can be aliased with b̄ once the sweep adjoint has read it, which brings this to
  about 260;
- Q̄: 40 B/cell.

**Checkpointing over many steps.**
- **A static step** is a function of (Qⁿ, dt) only, so a checkpoint is Q: 40 B/cell, or 0.67 GB at 256³. dt per step is a scalar,
  stored.
- **A moving step** also needs the generators' positions: 24 B/cell, quantised to the 2³⁰ grid, so exact as 3 int32 (12 B/cell). The
  mesh itself is not stored: on a moving mesh it equals a rebuild from the quantised positions (hydro_test: "the mesh equals an exact
  rebuild"), so the reverse pass rebuilds or repairs it from a checkpoint's positions. A moving checkpoint is about 52-64 B/cell.
- **Budget on one A100** (40 GB). The memory left for checkpoints after the forward run and the adjoint rows sets s, the number of
  snapshots Griewank's binomial schedule can hold. With r recomputations it covers C(s + r, s) steps:
  - 128³ moving: 2252 B/cell is 4.7 GB, the adjoint rows 0.9 GB, about 33 GB free, s ≈ 250 → with r = 2 about 31000 steps;
  - 256³ static (after `release_mesh`): about 1250 B/cell forward in double, 21 GB, plus 7 GB of adjoint rows, about 12 GB free,
    s ≈ 18 → r = 3 covers 1330 steps, r = 4 covers 7300;
  - 256³ moving: 2252 B/cell is 37.8 GB, so no room on the device. Checkpoints go to host memory (512 GB a node, about 1.1 GB per
    snapshot at 25 GB/s ≈ 45 ms each, small against a moving step at 256³) or to multiple GPUs.
  - LUNA's revolve: 2000 steps at 256³ in 36 GiB, grad/forward 6.5-8.8. Its snapshot is also one state (82 MiB at 128³). The
    difference is the reverse of one step. LUNA's VJP keeps the XLA step's temporaries (its 1-step JVP peaks at 15.7 states).
    luna-cpp's reverse step adds 420 B/cell of rows, about 10.5 states of 40 B, to the forward's own scratch [I]. On the forward, LUNA
    carries about 25 N³ temporaries, against luna-cpp's 2252 B/cell moving.
- **Two tiers:** device snapshots for the inner revolve and host snapshots for the outer one. The reverse cost is then (r + 1) forward
  steps plus one adjoint step per step.

**Use cases of reverse mode:**
- gradients of one scalar (a loss, an error norm) with respect to whole fields: initial conditions (LUNA's Jeans IC inversion),
  per-cell sources, mesh-velocity fields (L3);
- error sensitivities for adaptation (L8);
- calibration with many parameters (L5/L9).

### The moving step at fixed topology

The moving step adds dependences through the mesh:
- point velocities from W (AREPO's w = v plus regularisation);
- positions x + w dt, quantised to the 2³⁰ grid;
- the geometry of the new mesh: areas, face centroids, volumes and centroids, as functions of the positions;
- the two flux passes (MovingFlux) on the old and new mesh, with face velocities.

At fixed topology every one of these is a smooth function except the quantisation (a floor) and the regularisation's switch
(`max_angle` against 0.75 × factor).

**Plan:**
1. **Derivatives of the geometry with respect to the generator positions,** in voronoi-cpp: d(area vector, face centroid, volume,
   centroid)/dx. They follow from the circumcentres of the Delaunay tetrahedra, which are rational in the four vertices. Tangent and
   adjoint per tetrahedron and per face, verified as here (FD and dot test), at fixed topology. This is a mesh-library change, so a
   voronoi-cpp issue is wanted.
2. **The quantisation:** its true derivative is 0 almost everywhere, which would cut the dependence of the mesh on the flow. Use the
   identity, d(floor(x 2³⁰)/2³⁰)/dx := 1 (a straight-through rule), and state it. The error of that rule is one grid step, 2⁻³⁰ of the
   box.
3. **The point velocity's regularisation:** treat its switch as the limiter's (the derivative of the branch taken).
4. **MovingFlux tangent and adjoint:** the same per-face functions plus the face velocity w_f, which needs `flux_tangent` and `flux_adjoint` with respect to w and n. These are not in L1, where n and w are fixed. They are mechanical extensions: `to_lab` and the side velocities are linear in w.
5. **Test** as here: FD on a small moving mesh with a step that makes no flip, plus the dot test.

### What a derivative across a flip means

A flip changes the topology: which pairs of cells share a face. It is decided by exact integer predicates, so it has no derivative.

**The geometry is continuous across a flip.** At the flip the four or five generators are cospherical, the face that appears or
vanishes has zero area, and volumes and centroids are continuous. So the hydro step is continuous across a flip in exact arithmetic,
except for the forward's own discontinuous rules (the tiny-face rule at 1e-6 of the surface, the fallbacks).

**The derivative is one-sided:** the derivative of the topology the forward used. Over many steps the gradient is the sum of these
piecewise derivatives, which is a valid generalised gradient wherever the forward is continuous. A gradient-based optimiser sees a
kink at a flip, not a jump.

**Two caveats:**
1. **The tiny-face rule makes a new face's entry into the limiter range a jump.** A smooth weight, ramping the face in over [1e-6,
   2e-6] of the surface, would make it continuous, but it changes the scheme, so it is the owner's call.
2. **FD across a flip measures the jump of the discontinuous rules,** not the derivative. Tests must use steps without flips, or count
   and skip them, as here.

A space-time formulation (O2/J4, swept control volumes) would make the flux through a face that appears continuous in time by
construction; the research row stays.

### Kokkos and the A100

The derivatives are plain `KOKKOS_INLINE_FUNCTION` code in the same kernels as the forward. The CUDA build and run are in the A100
section. No Enzyme, no LLVM toolchain and no change to nvcc_wrapper are needed.

**Registers:** the HLLC adjoint holds the forward waves, the side and the bars at once. If it spills, split the face adjoint into a
waves pass and a sides pass, or recompute the side inside each branch.
